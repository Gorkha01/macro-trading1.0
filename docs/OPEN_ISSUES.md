### O-39 — `inflation_surprise_bp` — BLOCKED (no free consensus forecast)

A **genuine** inflation surprise is `actual − expected`, and the expected leg is a
consensus forecast. **O-8** already records that no free source for consensus
exists, so this input cannot be supplied as defined.

**Registered `blocked:` in `config/series_registry.yaml` (D-052)**, with the probe
evidence written verbatim rather than summarised — four queries, four different
failure modes:

| query | result |
|---|---|
| `"CPI forecast"` | `EmptyDataError` |
| `"CPI consensus"` | `EmptyDataError` |
| `"consumer price index forecast"` | "No results found" |
| `"inflation expectation"` | returns only `T5YIFR` / `EXPINF*YR` |

**The fourth row is the one that matters**, because those series *look* like a

claim about the world and it decays** (O-21, three occurrences): this entry should
be re-probed with `fred_search` in the same way `median_cpi_direction` and

false.

**Affects:** `cross_asset_transmission` (Module 5.6). The function keeps the input

**reported but not used** — the disclosed form of a *declared, consumed,
unreachable* input. The undisclosed form is forbidden: mutation `M1.1` folds the
surprise into the nominal leg, and no test may pass while it does.

### O-6 — Pre-launch data vintages are unrecoverable — LIMITATION

> **STATUS 2026-09-22 — PARTIALLY RESOLVED (D-088). The limitation below still
> stands and is unchanged; what changed is that `vintage_datetime` is no longer
> *unreachable*.** The `pop()` finding this entry records was correct and was
> re-verified — OpenBB still discards the vintage fields. But the conclusion
> drawn from it ("Reaching it would require the engine to hold its own FRED key,
> which §22.2/22.3 forbid — **Recorded, not implemented**") was too strong: the
> key can be **borrowed from OpenBB's own credential store** rather than
> duplicated, which honours the rule instead of waiving it. A direct ALFRED route
> now exists at `data_layer/alfred_client.py` and is **verified live**:
> CPIAUCSL 2024-01..03 read at vintage 2024-06-01 returns 309.685/311.054/312.230
> against 309.698/310.967/312.345 at the latest vintage. Two registry series are
> declared `vintage_eligible` (CPIAUCSL, GDPC1) and the route is **off by
> default**.
>
> **What this does NOT change — read this before relying on the above.** The
> *Limitation* heading is still accurate. Item 14 of the §21.4 Loophole Ledger —
> *"Pre-launch data vintages — unrecoverable"* — remains true in the sense that
> matters: **this process's own pre-launch history cannot be backfilled.** ALFRED
> supplies FRED's revision history, not this engine's. The forward parquet trail
> in `data/raw/` is still the only record of what *this system* saw, and the two
> are complementary rather than substitutes. A thesis that depends on either must
> still disclose the dependence in `MacroThesis.warnings`.

Revision analysis (`prior_month_revision`, `two_months_ago_revision`) works
**only forward**. Vintage storage begins from the first snapshot this system
persists and cannot be backfilled.

**Consequence:** before enough history accumulates, revision reads must return
`None` — **never zero**. A zero would be indistinguishable from "no revision
occurred", which is a materially different claim.

**Mitigation in place:** `data_layer/persistence.py` writes timestamped
parquet snapshots keyed by retrieval time, which is what makes this history
exist at all. See `docs/BUILD_STATE.md`.

**Re-probed 2026-09-20 (Phase 0–4 final audit) — the block is a claim about the
environment and it was re-derived rather than inherited.** The audit was given a
prescribed procedure for reading a specific vintage:

> `GET /api/v1/economy/fred/series_vintages?symbol=SYMBOL` → then
> `GET /api/v1/economy/fred/series?symbol=SYMBOL&realtime_start=…&realtime_end=…`

**That route does not exist, and the parameter is silently ignored.** Measured
against the live service on `:6901`, five independent ways:

| probe | result |
|---|---|
| enumerate all **278** live OpenAPI operations | **zero** paths contain `vintage` |
| any operation declaring a `realtime*` parameter | **zero** |
| `/api/v1/economy/fred_series` accepted params | `provider, symbol, start_date, end_date, limit, frequency, aggregation_method, transform, all_pages, sleep, chart` — **no `realtime_start`/`realtime_end`** |
| `GET …/fred_series?…&realtime_start=…&realtime_end=…` | accepted and returned the **latest** revision — see the *absorption* proof below |
| The prescribed **HTTP paths** (`/economy/fred/series_vintages`, `/economy/fred/series`) | **HTTP 404** — neither path exists; the real path is `/economy/fred_series` |
| OpenBB **SDK** namespace `obb.economy.fred` | **does not exist** — `AttributeError: 'ROUTER_economy' object has no attribute 'fred'`; the FRED surface is exactly `fred_regional`, `fred_release_table`, `fred_search`, `fred_series` |

#### CORRECTION 2026-09-20 (later re-probe): two earlier claims in this entry were too strong

The first version of this block said (a) *"zero operations declare a `realtime*`
parameter"* and (b) *"the direct FRED hosts are not an escape hatch."* **Both
were overstated and are corrected here.** Reading the provider source
(`.venv/Lib/site-packages/openbb_fred/models/series.py` and `search.py`) showed:

- **`realtime_start` / `realtime_end` DO exist in the OpenBB FRED provider** —
  but only as `order_by` **sort keys** on `fred_search` (line 41–42, 76–77), never
  as filter parameters. `fred_search`'s response *does* carry `realtime_start` /
  `realtime_end` columns, and for CPIAUCSL they read `2026-09-20` / `2026-09-20`
  — i.e. **today**, meaning *"this metadata is valid now"*, the **current vintage
  boundary**. That is a vintage **marker**, not a vintage **selector**: it tells
  you which vintage you are in, not how to ask for a different one.
- **`fred_series` (the provider) *pops* `realtime_start`/`realtime_end` out of the
  API response** (`series.py:156-157`) and never sends them upstream: its query
  string is built as `get_querystring(query.model_dump(), ["series_id"])` from a
  query model that **declares no realtime field**. So the parameters cannot be
  transmitted by this provider at all.

#### The absorption proof (this is the part that matters)

Passing `realtime_start`/`realtime_end` through the SDK does **not** raise — the
extra kwargs are swallowed and the request succeeds:

```
fred_series(symbol='CPIAUCSL', start_date='2024-01-01', end_date='2024-06-01')
  -> (6, 1)   Jan-2024 = 309.698, Feb = 310.967, Mar = 312.345
fred_series(..., realtime_start='2024-01-01', realtime_end='2024-01-01')
  -> (6, 1)   Jan-2024 = 309.698, Feb = 310.967, Mar = 312.345
  -> .equals() == True   (byte-identical)
```

**And the identical output is absorption, not a genuine "no revision" result** —
proved by calling FRED's ALFRED-capable endpoint directly with the key from
OpenBB's own credential store:

```
CPIAUCSL, observations 2024-01..03, asked at three different vintages:
  vintage 2024-06-01 -> {2024-01: 309.685, 2024-02: 311.054, 2024-03: 312.230}
  vintage 2024-12-01 -> {2024-01: 309.685, 2024-02: 311.054, 2024-03: 312.230}
  vintage 2026-09-20 -> {2024-01: 309.698, 2024-02: 310.967, 2024-03: 312.345}
```

**The same observation dates carry different values per vintage.** Real revision
history exists (Δ ≈ 0.013 / 0.087 / 0.115 index points). OpenBB returned **one**
value — the latest — while the caller believed it had asked for 2024-01-01. This
is the sharpest form of the danger this ledger exists to record: **a silently
absorbed parameter is indistinguishable from a respected one unless you compare
payloads, and the HTTP status is 200 either way.**

#### FINAL WORD (2026-09-20, third probe) — every spelling of the endpoint, tested

The user supplied endpoint spellings *without* the `/api/v1/economy` prefix and
asked for them to be checked against `/docs`. **All spellings tested; only one
exists, and it ignores the vintage parameters.** Complete matrix:

| URL tested | Status | Behaviour |
|---|---|---|
| `/fred_series_vintages?symbol=CPIAUCSL` | **404** | path absent (needs the prefix) |
| `/fred_series?symbol=CPIAUCSL&realtime_start=…&realtime_end=…` | **404** | path absent (needs the prefix) |
| `/api/v1/economy/fred_series_vintages?symbol=CPIAUCSL` | **404** | **no such endpoint exists under any prefix** |
| `/api/v1/economy/fred_series?symbol=CPIAUCSL&realtime_start=…` | **422** | *not* 404 — it exists, but `provider` is a required query param |
| `/api/v1/economy/fred_series?provider=fred&symbol=…&realtime_start=…&realtime_end=…` | **200** | **parameters ACCEPTED and IGNORED** — see below |

**The 422 is important and worth stating plainly:** a 404 means "this route does
not exist"; a 422 means "this route exists and I read your query". The user's
instinct that these are REAL local endpoints is **correct for `fred_series`** —
it is real, it is on the server, and `GET /docs` serves it. What is not real is
the vintage **capability**: `fred_series_vintages` is absent under every prefix
(and `vintage` appears in **0 of the 278** documented paths).

**The acceptance-and-ignore proof, three-way, same query:**

```
GET /api/v1/economy/fred_series?provider=fred&symbol=CPIAUCSL&start_date=2024-01-01&end_date=2024-03-01
  A) no realtime                      -> [309.698, 310.967, 312.345]
  B) realtime_start/end = 2024-01-01  -> [309.698, 310.967, 312.345]
  C) realtime_start/end = 2026-09-19  -> [309.698, 310.967, 312.345]
TRUE 2024-01-01 vintage (FRED/ALFRED) -> ['309.685', '311.054', '312.230']
```

**Byte-identical across A, B and C.** Three different vintages requested — a real
one in the past, a near one, and none at all — and the server returned the
identical latest revision each time, with `warnings: null`. **The endpoint is
real; the vintage parameter is not connected to anything.**

**The SDK behaves the same way, and this is the dangerous part:**

```
obb.economy.fred_series(provider='fred', symbol='CPIAUCSL', realtime_start='2024-01-01')
  -> NO TypeError. Accepted silently. Returned 955 rows from 1947-01-01.
```

An unknown kwarg that is **rejected loudly** is safe — the caller learns
immediately. One that is **accepted and discarded** is a trap: the call
succeeds, the data looks plausible, and the only way to detect the substitution
is to compare the payload against a known vintage. **`obb.economy.fred_series`
DOES exist and DOES work** (it returns the correct current CPI: `334.131` for
`2026-08-01`); it simply has no vintage dimension.

**Config note:** the `provider` requirement is satisfied in this codebase because
`config/series_registry.yaml` carries `provider: fred` on every series and
`openbb_client.py` passes it explicitly — so the engine is already on the
correct, real path. **No code change is warranted or made.**

#### What IS reachable, and why the engine still does not use it

`https://api.stlouisfed.org/fred/series/observations` **with** `realtime_start`/
`realtime_end` **does** return true vintage data — demonstrated above. So the
capability is not absent from FRED; it is absent from **the OpenBB route this
engine is specified to use** (§5.1, and the directive's own "Use OpenBB's own
credentials / do not add a duplicate `FRED_API_KEY` requirement"). Reaching it
would require the engine to hold its own FRED key and call the provider directly,
which is exactly the architecture and credential-duplication §22.2/§22.3 forbid.
**Recorded, not implemented.**

**Consequence, unchanged and now measured rather than assumed:** `vintage_datetime`
stays `None` throughout, which the schema documents as UNKNOWN. The
`published-but-not-vintage` distinction the codebase already draws
(`publication_dates.py`, `release_calendar.py`) is the correct handling: it
reports *when a value became public* (available, from the series' own
`last_updated`) and refuses to report *which revision it is* (unavailable).
Substituting the first for the second remains the prohibited substitution.

**What this does NOT close:** nothing above says a vintage store is impossible —
only that **no reachable route on this build exposes past revisions**. The
forward-looking mitigation stands, and `O-13` records the same conclusion reached
from the GDPNow direction.

### O-7 — `gdp_potential` mixes measurement with projection — MITIGATED

Discovered by live execution (see `DECISIONS.md` D-002). FRED `GDPPOT` carries
CBO forward projections extending ~10 years beyond the current quarter — a live
snapshot retrieved 62 observations, **41 of them future-dated**.

**Resolved 2026-09-16.** Every consumer of `gdp_potential` filters to
`observation_date <= as_of` through `models.as_of.observation_as_of()`, so no
projection can be treated as realised capacity. A naive "take the latest value"
read would compute the output gap against the Q4 2036 projection.

**Where the filter lives:** `models/as_of.py`, not inside any one model. The
obligation was general — "every consumer of `gdp_potential`" — so the fix is
general too: a consumer gets the discipline by using the shared helper rather
than by remembering to write a comparison. `AsOfSeries` returns the withheld
count and horizon alongside the filtered points, so a model can disclose the
truncation instead of silently discarding it.

**Two further consequences found while implementing it** (both recorded as
decisions rather than absorbed):

* **D-009** — filtering alone was not sufficient. `GDPPOT` runs one quarter
  *ahead* of `GDPC1`, so the filtered series still had no same-quarter partner
  for its latest point. The gap must pair the latest **common** quarter; taking
  each series' own latest produced +0.29% where the correct answer is +0.83%.
* **D-010** — the registry had recorded the Q4 2036 projection as
  `verified_value`, i.e. the *evidence* for the verification claim. Corrected to
  the latest realised observation, with `verified_observation_date` and
  `verified_curve` now required for a `forward_looking` verified series.

**Verification:** `test_output_gap_from_snapshot_ignores_forward_projections`,
`test_output_gap_pairs_the_same_quarter_never_each_series_own_latest`,
`test_live_output_gap_is_computed_from_same_quarter_realised_data`, plus the
D-010 registry validators. Mutation-testing the filter's removal fails 4 tests.

**Residual limitation:** `gdp_potential` remains NSA while `gdp_real` is SAAR.
That is reported in the registry's `seasonality` field and assessed as
second-order (the gap shows no systematic quarterly pattern: Q1 +0.96,
Q2 +0.95, Q3 +1.21, Q4 +1.37 over 20 quarters). It is a documented limitation,
not a correction to apply — a seasonally unadjusted *potential* series has no
seasonal component to remove.

### O-8 — Consensus estimates unavailable — LIMITATION

No free source for consensus/analyst expectations. Economic **surprise**
calculation (actual minus expected) therefore cannot be computed.

**Consequence:** the system can report that CPI printed 3.71% YoY, but cannot
report whether that was above or below expectations. Much of the market reaction
function depends on the surprise, not the level. Any thesis relying on a
surprise component must disclose that it is absent.

**Phase 5+ is an UPGRADE PASS, not a tier of new work.** Phases 0–4 built the
*simple* version of each of these; Phase 5+ replaces it with the sophisticated
version. **Nothing from Phases 0–4 is deleted** — the simple function keeps working
and the advanced one supersedes it. That is why the phase is called *"Phase 5+"*
rather than a tier: it is a **pass over existing components**, not a new layer.
