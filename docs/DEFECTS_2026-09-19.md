### 1.0 Correction to my own first framing

My first draft of this section said the missing plumbing layer was a *general*
gap and implied the transforms (yoy/mom/percentile) did not exist. **That was
wrong, and I am correcting it rather than leaving it.**

The plumbing layer **does exist**: `src/macro_engine/api_layer/orchestration.py`,
1044 lines, with exactly those transforms implemented and documented —
`_mom_percent`, `_yoy_percent`, `_trailing_percentile`, `_claims_4wk_change`,
`_percentile_window_months`, `_inflation_leg`, `_labor_leg`,
`_output_gap_change`, `_policy_rate`, `_short_yield_from_curve`. The
`derivation_notes` in a live thesis prove they run, and their `window` strings
document the release-lag handling I claimed was absent (e.g. *"JTSQUR is
published as a RATE IN PERCENT (measured 1.9), and the model wants a
percentile — 1.9 satisfies the ge=0/le=100 validator, so the wrong quantity
passes silently"*).

So `builder.py:246`'s "plumbing layer that does not exist yet" is **stale
documentation**, not a description of the current tree. The builder was written
before the orchestrator and its docstring was never updated.

**The accurate finding is narrower and more specific:** when first measured, the
orchestrator wired the **policy axis only**. It imported from exactly five model
modules —

```
as_of · contracts · gdp_nowcast · instrument_selection · labor_synthesis · policy_rules
```

— and derived precisely the inputs `build_us_macro_thesis` demanded:
`EconomyReads` (3 slots), `TaylorRuleInputs`, `FirstDifferenceInputs`,
`short_yield`. Nothing derived a `RegimeInputs`, a curve decomposition, an FCI,
a risk input, or a GDI growth pair. That is *why* dozens of functions were
unreachable: not because the transform machinery is missing, but because **no one
extended the orchestrator to feed the other axes.**

**Since first measurement, five of those have been added** and now *are* wired:
`classify_regime_rule_based` (`_regime_leg`), `gdp_gdi_divergence`
(`_national_accounts_leg`), `curve_slope` and `breakeven_inflation`
(`_curve_leg`), and the point-in-time pairing helper they route through. The
orchestrator's import set now includes `regime`, `national_accounts` and
`yield_curve`. The unreachable count moved **63 → 59** accordingly.

### 1.1 Is this a bug, or is it deferral?

**Neither, cleanly — and the distinction matters.** The spec (`AGENTS.md` §21.3,
the "Tier" list) defines Tier 1–4 as buildable in Phases 0–3 and Tier 5 as
Phase 5+ stubs. Cross-referencing the 59 unreachable functions against that list:

| Tier | Unwired | Verdict |
|---|---|---|
| Tier 1 | 21 | mostly Phase 0–3 gap — but 3 are Phase 4+ risk functions |
| Tier 2 | 19 | mostly Phase 0–3 gap — but 4 are Phase 4+ risk/portfolio |
| Tier 3 | 6 | **Phase 0–3 gap** |
| Tier 4 | 3 | trade constructors — Phase 3–4 |
| Tier 5 | 0 | — (the Tier 5 stubs are correctly stubbed) |
| not in the Tier list | 6 | helpers / later additions |

**All 59 are Tier 1–4 in `§21.3`'s sense — but `§21.3`'s tiers are not the same
axis as the endpoint column.** `§22.1` says the tier table decides *when a stub
becomes IMPLEMENTED* and nothing more. `AGENTS.md:1787` separately assigns
Modules 17–18 (the risk/portfolio functions) the endpoint **`(Phase 4+)`**. So
"Tier 1–4" and "owed in Phases 0–3" are different questions, and the risk
functions are Tier 1–2 **and** Phase 4+ at the same time. See DEF-001.

Note that **no Tier 5 function is falsely wired**, which is a real sign of
discipline: the team did not fake progress by calling stubs.

**`gdp_gdi_divergence` is the archetype.** Implemented in
`models/gdp_nowcast.py:576`, with a full mutation sweep
(`scripts/mutation_gdp_gdi_divergence.py`) defending six corrections. Its only
caller in the entire repository is `scripts/live_labor_check.py:1422`. The
thesis never sees it. And now that DEF-002 is fixed, GDI *data* exists in the
snapshot — so the only remaining blocker for this model is the wiring.

The honest framing: this is not fraud and not a crashed system. It is **a
well-built library behind a pipeline that only consumes one of its axes.** The
thesis discloses its own gaps (see §3), so a careful reader is not misled — but
the *capability count* and the *delivered count* differ by roughly 5×, and no
prior report said so.

#### A second defect found *while* fixing DEF-003 — the regime had become a gate

**Severity: HIGH (caught by the suite, not in production).** The first version of
`_regime_leg` read its inputs through `_realised()`, which **raises**
`OrchestrationError` on an empty series. Because it returns a non-optional
`ModelResult`, a missing `unemployment_rate` made `snapshot_to_thesis_inputs()`
raise — i.e. **one absent optional series could block the entire thesis**.
Measured: 28 tests failed with `OrchestrationError: snapshot field
'unemployment_rate' is empty, so no thesis can be built`.

This inverts §16.2's ordering — the four reads precede Q6's significance test,
and Q6 is what stands a thesis down — and it contradicts the rule
`_output_gap_change` already states for the same situation: *"refusing would
make the whole thesis unavailable over a term Section 6.1 weights separately."*

Fixed by making the regime leg degrade instead of gate:
- `_regime_leg` now returns `ModelResult | None`; `None` means "not classified".
- New `_realised_or_none()` converts the two documented absences (empty series,
  entirely forward-dated) into `None`, and **only** those — a malformed snapshot
  still propagates rather than masquerading as "no data".
- Each abstention writes an explicit `NOT_COMPUTED` derivation note naming the
  field and the count, so the reason reaches the reader.
- `snapshot_to_thesis_inputs` guards `regime is not None` before reading
  `.warnings`, so degradation touches only the regime field.

`cpi_headline` absence remains fatal — but from `_inflation_leg`, where
`pi_current` feeds both policy rules, **not** from the regime leg. Four tests pin
all of this (`tests/api_layer/test_orchestration.py`):
`test_an_absent_unemployment_rate_yields_a_thesis_not_an_error`,
`..._cpi_headline_refuses_in_the_policy_leg_not_the_regime_leg`,
`..._short_cpi_history_refuses_in_the_policy_leg_not_the_regime_leg`,
`test_a_present_regime_is_classified_and_its_warnings_ride_along`.

#### DEF-004a — the two tenor vocabularies, and the silent check they disabled
**Severity: HIGH (latent — nothing could reach it before this wiring).**

Wiring the curve leg exposed a defect that had been **arithmetically
unreachable** and is worth stating carefully, because both sides are individually
correct:

| Source | Vocabulary | Why it is right |
|---|---|---|
| `settings.instrument_selection.curve_default_short_tenor` | `2y` | Interpolated into `"Duration-weighted 2y/10y UST steepener"` — the desk spelling. |
| `models/yield_curve.py::_tenor_years` | `2y` | Parses the config's own form; **refuses** `"2yr"` explicitly. |
| `series_registry.yaml` | `2yr: DGS2` | FRED's tenor spelling; the data layer's canonical form. |
| `data_layer/validation.py` | `tenors["2yr"]` | Reads the registry's keys. |

Nothing had ever compared the config's strings to the curve's keys, so the two
vocabularies had never met. `D-058` even recorded that the config strings are
*"interpolated into an instrument name and are never parsed"* — true only because
no consumer existed.

**Measured, before the mapping:** `curve_slope` fed the config labels raised
```
KeyError: short tenor '2y' is not in the supplied curve;
available: ['10yr', '1mo', '1yr', '20yr', '2yr', '30yr', ...]
```

**Why this is worse than a crash.** `validation.py` guards its 2s10s inversion
check with `if "2yr" in tenors and "10yr" in tenors:`. Under any key-vocabulary
change that guard is simply `False` and **the check silently does not run** — the
same fail-open class as the dead `if not points:` guard found in `_regime_leg`.
A conditional that fails open reads as a passing check.

**Fix:** `_config_tenor_for()` translates at the seam (config `2y` → curve
`2yr`), returns the label unchanged on an exact match so a caller already speaking
the curve's vocabulary is not second-guessed, and returns `None` when no mapping
is unambiguous — so the leg **abstains rather than substituting a tenor**. Neither
vocabulary was changed: editing the config would break the instrument name, and
editing the registry would break validation.

**Proven non-vacuous:** removing the mapping makes 40 tests fail.

### DEF-007 — the canonical point-in-time lookups had zero callers while the orchestrator reimplemented them
**Severity: MEDIUM (correctness — duplication, not a wrong number).**
`models/as_of.py` defines `observation_on_or_before` (line 185) and
`latest_observation` (line 170) as the documented helpers for "the latest
observation at or before a target". Measured: **neither has a single caller
anywhere in the repo** — the only mention outside `as_of.py` is a docstring that
names them.

Meanwhile `orchestration.py` hand-rolled the same boundary rule **three times**:
`_value_on_or_before` (line 331, justified and documented), `_output_gap_change`'s
earlier-quarter pair, and — written by me this session — `_national_accounts_leg`'s
year-ago pair. The last two were the identical
`[d for d in dates if d <= target][-1]` shape.

**Why it matters rather than being tidiness:** a boundary rule copied three times
is three chances to get `<=` versus `<` wrong in only one of them, and the bug
that motivated this whole review (`replace(year=...)` silently pairing
observations ten quarters apart) is exactly this class. **Fix:** added one
date-keyed helper, `_latest_on_or_before`, and routed both call sites through it;
proved equivalent to the old inline form on 7 boundary cases including the exact
anniversary (0 mismatches) and re-verified live (same pair, same `−0.052pp`).

Note the orchestrator's two helpers are **not** a pointless duplicate of
`as_of.py`'s: those take `ObservationPoint` sequences, while these two call sites
hold a plain *set of common dates* — the intersection of two series — which no
per-series helper can answer. The docstring on the new helper says so, so the
next reader does not "fix" it into a type error. That distinction is why the new
helper is date-keyed rather than an import.

### DEF-008 — the FCI cannot be wired in Phases 0–3, and the reason is data, not code
**Severity: MEDIUM (scope/expectation — the last remaining Phase 0–3 item is
blocked, which contradicts how §6 item 1 framed it).**

`compute_fci` is the only model left that I had described as an in-scope Phase
0–3 wiring obligation. Checked against the live tree, **it cannot be honestly
wired**, for four independent reasons — any one of which would be sufficient:

**1. Three of its five inputs have no series at all.**
`FCIInputs` requires exactly five `FCIComponent`s (`policy_rate`,
`credit_spread_hy`, `term_premium`, `equity_index`, `usd_index`). Measured
against `config/series_registry.yaml` (48 series) and `settings.yaml`'s
`snapshot_fields.us` (22 series):

| Component | Series | Status |
|---|---|---|
| `policy_rate` | `DFF` | present |
| `credit_spread_hy` | `BAMLH0A0HYM2` | present |
| `term_premium` | — | **no series anywhere**; §22.5 defers the ACM premium to Phase 5+ |
| `equity_index` | — | **no series**; registry has `equity_volatility` (VIX), not an index level |
| `usd_index` | — | **no series**; no dollar-index series exists |

**2. Two more are structurally empty by design.** `equity_index` and `fx_spot`
are in `persistence.MAPPING_SERIES_FIELDS` but absent from
`snapshot_fields.us`, so they never fetch — that is DEF-005. So even if series
were registered, the snapshot would not carry them for a US-only thesis.

**3. The model refuses a subset, so nothing can be substituted.** `compute_fci`
compares the configured component set to the modelled set and raises on any
mismatch (verified in `financial_conditions.py`). Supplying only the two
available components is not a degraded FCI — it is a refused call. And
substituting a different-tenor premium or a proxy index is exactly the
fabrication §21.4's Loophole Ledger forbids.

**4. §6.x's own stated destination does not exist.** The spec's mapping note
(`AGENTS.md:2405`) says the FCI *"feeds a new `MacroThesis.financial_conditions_view`
field (add to Section 7.1's schema)"*. `MacroThesis` has **no such field** — its
views are `regime`, `growth_view`, `inflation_view`, `policy_view`, and
`model_config` is `extra="forbid"`. And §16.2's authoritative pipeline pseudocode
**never calls `compute_fci`** at all. So "wiring" it would require a schema
change the spec defers and a caller the spec's own algorithm does not have.

**Verdict: this is a Phase 0–3 function blocked on Phase 5+ data, not a wiring
gap.** The model is correct and well-built — exercised directly, it publishes
`nfci_cross_checked: false` and warns that the mandatory NFCI cross-check did not
run, rather than pretending. Wiring it today would require inventing three
series, which is the one thing this system is designed not to do.

**Correction to §6 item 1 (second time).** That item listed "the FCI" as the
remaining Phase 0–3 work. It is not available work — it is blocked work. The
accurate statement is: **there is no unblocked Phase 0–3 wiring work remaining**;
what is left is gated on data acquisition (a term premium, an equity index, a
dollar index, and NFCI), which is a data-sourcing task, not an orchestration one.

**What would unblock it:** add `term_premium` (ACM), an equity index level, a
dollar index, and `NFCI` to `series_registry.yaml` + `snapshot_fields.us` — each
as a registry entry, which is the one-config-file change Part B claims. Then the
FCI leg is a normal `_fci_leg(snapshot)` in the existing style. That is a
concrete, bounded task if you want the FCI live.

**(a) Is Kelly the real Kelly formula, or a placeholder? — REAL.**
