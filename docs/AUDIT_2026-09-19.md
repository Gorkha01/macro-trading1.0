## Gates — re-measured at the START of this audit (not carried forward)

```
uv run python tools/sweep_health.py   -> 38 sweeps, 0 failures, 0 leftovers   OK
grep -rn "if False:\|if True:" src/   -> nothing
uv run pytest -q                      -> 2053 passed, 1 skipped, 0 failed
```

**On the first cold run of the session the suite reported `23 failed`.** All 23
were `tests/api_layer/*` plus one live data-layer test. **The first explanation
recorded here — "live FRED fetch under first-run load" / network warmth — was
wrong, and the discipline of not accepting it is what found a real defect.**

The decisive experiment: `data/raw/` was moved aside entirely (it is
git-ignored, so this reproduces a fresh clone) and `tests/api_layer` re-run. The
result was **22 failed** — the original failure count, reproduced at will, with
no network involved at all. It was never flaky.

**Root cause.** Two defects compounding:

1. **`load_snapshot` cannot signal an absent store.** With no parquet file,
   `_latest_parquet` returns `None`, `load_latest_snapshot_frame` returns an
   empty frame, and `snapshot_from_long_frame` returns a *default empty*
   `MacroDataSnapshot()` — successfully, with no error. The test fixture's guard
   was `except (FileNotFoundError, ValueError)`, which catches exceptions that
   are never raised. **The `pytest.skip` was dead code.**
2. **An empty snapshot is then seeded as though it were real.** `_seed()` puts
   that empty snapshot in the provider cache, so `/dashboard_data` honestly
   reports `yield_curve: None` (there is no curve in an empty snapshot) and the
   tests fail with `assert body["yield_curve"] is not None` → `assert None is
   not None`. **The tests blamed the API for a fixture that had quietly
   degraded.** 22 tests failed for one reason, reported as 22 reasons.

**Fixed**, not flagged forward:

- `SnapshotStoreEmptyError(FileNotFoundError)` and `has_persisted_snapshot()`
  added to `persistence.py`; `load_snapshot(..., strict=True)` raises on an
  absent store. The default stays permissive, because an empty snapshot is a
  legitimate audit fact ("we fetched and got nothing") that
  `long_frame_from_snapshot` deliberately records.
- The `tests/api_layer` fixture now uses `strict=True`, so the guard is live.
- 3 regression tests pin the distinction, **proven RED** by planting the
  regression (`if False and strict` → `Failed: DID NOT RAISE
  SnapshotStoreEmptyError`), then restored.

**Verified both directions:** store present → `127 passed`; store absent →
`87 passed, 40 skipped, 0 failed`.

**Residual, genuine, and much narrower:** `tests/data_layer::test_live_snapshot_*
` are `@pytest.mark.live` and do fetch real data; they are the only tests whose
outcome depends on the network, which is by design (Section 21.0). O-90 (the
process-global snapshot cache) remains a real design observation — see open
items.

## Findings — what was wrong, and what was done

### AUDIT-001 — `validate_snapshot()` bypassed the registry (HIGH) — **FIXED**

`validate_snapshot` hardcoded four series-name tuples covering **18 of the
registry's 45 entries** and called `validate_observations` **without** the
registry's `forward_looking` / `future_date_tolerance_days`.

Measured, same snapshot, two verdicts:

```
build_snapshot()   -> [INFO] gdp_potential: FORWARD_LOOKING_HORIZON — 41 projections
validate_snapshot()-> 30x [ERROR] gdp_potential FUTURE_OBSERVATION_DATE  (has_errors=True)
```

The ERROR verdict was false. `gdp_potential`'s projections are *required* for the
output gap.

**Fix:** `validate_snapshot` now derives its series list from the snapshot schema
+ the registry and reads `plausible_range`, `forward_looking`,
`future_date_tolerance_days` from each entry. Findings: **34 → 4**, then → **2**.
New series are now validated by adding one registry entry — the Part B contract.
Guarded by 3 new tests, each **proven to go RED** when the regression is planted.

### AUDIT-002 — `iorb` tolerance was 1; live data needs 3 (MEDIUM) — **FIXED**

```
retrieval 2026-09-19 -> IORB returns observations dated 2026-09-20 AND 2026-09-21
```

IORB is an **administered** rate the Fed schedules in advance; it is not a market
print. The declared tolerance of 1 armed the ERROR path against legitimate
values, producing the standing failure tracked as **O-84**.

**Fix:** registry `iorb.future_date_tolerance_days: 1 → 3`, with the live
evidence recorded in its `decision_note`. `sofr` correctly stays at 1 (it *is* a
prior-business-day market print). O-84 is resolved at its root.
Validated snapshot: **0 errors, 2 INFO.**

### AUDIT-003 — `datetime.utcnow()` — **CLEAN (suspicion false)**

4 occurrences, **all inside docstrings** quoting the specification's sample.
`no_trade.py:31` sits inside a module docstring spanning lines 1–139. Zero live
uses. `ruff`'s DTZ ruleset is enabled and passing.

### AUDIT-004 — Kelly formula — **REAL (suspicion false)**

`generalized_kelly_fraction` maximises `Σ pᵢ·log(1+f·rᵢ)` over f∈[0,1] by grid
search, with `1+f·r ≤ 0 → -inf` ruin detection. The `ev/100` placeholder is
absent from the tree entirely, as §22.13 requires.

### AUDIT-005 — `derive_market_implied_policy_path` — **STILL A PROXY (suspicion CONFIRMED)**

It subtracts an ACM term premium from a raw short yield, and with no premium
**returns the raw 2yr yield unchanged** (live: 4.67%) with 3 explicit warnings and
confidence 0.2. It does **not** read Fed Funds futures.

This is **disclosed, not hidden** — the docstring and the warnings both say so,
and §22.5 *mandates* this as the Phase 1–4 behaviour with the real
futures-implied distribution deferred to Phase 5+. **So: the suspicion is
factually correct, and the implementation is correct to spec.** No change made;
flagged for you because it is a genuine capability limit, not a bug.

### AUDIT-006 — "policy gap should use exactly the Taylor value" — **FALSE PREMISE (suspicion false)**

§22.4 mandates the **median of the three rules**, in as many words:
*"Median, not mean or Taylor-alone."* The implementation matches the spec
exactly. **Correct as-built; the premise was wrong.**

### AUDIT-007 — hardcoded confidence in `scorecard.py` / `builder.py` — **NOT A DEFECT**

Two live `confidence=1.0` literals exist, both documented as **census carriers /
adapters** whose confidence is deliberately a placeholder because
`compute_confidence()` is the sole real producer and neither value is published as
a measurement. Consistent with §22.8's intent.

## Spec (`AGENTS.md`) issues found by live testing

1. **§21.1 / registry: the `iorb` future-date assumption is wrong.** The spec
   treats iorb's lead as a same-day UTC-boundary artifact; live data shows a
   2-day forward publication because it is *administered*. Registry corrected.
2. **The registry is the single source of truth, but one consumer ignored it.**
   `validate_snapshot`'s hardcoded tuples were a second, stale source. Fixed.
3. **`plausible_range` was ambiguous for signed fields.** It is a LEVEL range,
   but the same field carries CHANGES (a narrowing spread is legitimately
   negative). Now explicit via the new `signed_series` registry property.
4. **`.env` is absent**, so FRED is unkeyed. It works (verified live) but the
   snapshot pulls ~45 series; without a key these will throttle on repeated runs.
   `.env.example` says so. **Recommend adding `FRED_API_KEY` before Phase 4.**

## Part B — pluggability, proven concretely

The requirement is that new **series**, new **models**, and new **countries** are
additive, not invasive. Measured, not asserted.

### B1 — Adding a new data series: **TRUE**

One entry in `config/series_registry.yaml` + one field on `MacroDataSnapshot` +
the field name in `settings.snapshot_fields.us`. `openbb_client.py` is **not
touched** — it is generic over `provider`/`endpoint`/`params`. After AUDIT-001's
fix the new series is also automatically validated and range-checked.

### B2 — Adding a new model/indicator: **MOSTLY TRUE — with one real seam**

**I actually did it.** Added `models/real_policy_rate.py`
(real policy rate = fed funds − core CPI YoY), which ran live:
**+1.18%** (3.63% − 2.45%). Files touched:
1. `src/macro_engine/models/real_policy_rate.py` — **new file, the whole indicator**
2. `tests/models/test_real_policy_rate.py` — **new file, 6 tests**

**No core file was modified.** It returns the standard `ModelResult`, and its
confidence comes from `compute_confidence`.

**The seam:** *consuming* a new indicator in the thesis does require core edits,
because the thesis's shape is fixed by §16.2:
- `builder.EconomyReads` declares exactly three slots (growth/inflation/labor),
  and `as_sequence()` returns a 3-tuple feeding 4 call sites.
- `scorecard._PILLARS` declares exactly four names and `ScorecardInputs` has
  exactly four typed fields.

A truly independent **5th pillar** would require editing `builder.py` and
`scorecard.py`. **This is not a defect to fix** — §16.2 defines the thesis as a
dual-mandate object with those reads, and widening it changes what the thesis
*means*. But the user's requirement as stated ("write one new function + register
it, no core edits") is **only partially met**: a new indicator that *feeds an
existing slot* (as `real_policy_rate` feeds policy) is purely additive; a new
*independent axis* is not. That distinction is the honest answer, and it is an
architectural decision for Phase 4+ rather than a bug.

### B3 — Adding a new country: **FALSE as stated**

**`INSTRUMENT_REGISTRY` does not exist anywhere in the codebase.** The user's
description of the mechanism is not what is built. What actually exists:

- `ProductionUniverse` (`thesis_layer/schemas.py:183`) — the *execution* universe
  (rates/fx/equity keywords), US-only by construction, with documented defaults.
- `select_instrument` (`models/instrument_selection.py:365`) — routes by
  `thesis_type` through an explicit branch per §22.3.1's table, and has an
  explicit `BLOCKED_MULTI_COUNTRY_NOT_BUILT` sentinel.
- `build_snapshot(country=...)` **raises `NotImplementedError`** for anything but
  `us`, by §22.3's own design.

So adding a country is **not** one registry entry, and §22.3 explicitly says it
must not be — each country needs its own verified data sources, its own
central-bank reaction function (the ECB's 20-country compromise, the BoJ's
deflation-scar bias, the PBoC's non-Western function are *different logic*, not
a relabelled Taylor rule), and its own instrument set. **The architecture is
honestly US-only and says so**, which is the correct posture (§22.3 retracted the
earlier multi-country claim for exactly this reason). The user's stated
expectation should be corrected: this is **by design**, and it is Tier 5.
